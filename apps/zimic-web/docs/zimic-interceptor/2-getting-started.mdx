## Your first interceptor {#http-your-first-interceptor}

### Declaring a schema {#http-declaring-a-schema}

To start using `@zimic/interceptor`, declare an HTTP schema using [`@zimic/http`](/docs/zimic-http/guides/1-schemas.md). The schema represents the structure of your API, including the paths, methods, request and response types.

:::tip TIP: <span>OpenAPI Typegen</span>

For APIs with an [OpenAPI documentation](https://www.openapis.org) (e.g. [Swagger](https://swagger.io)), the [`zimic-http typegen` CLI](/docs/zimic-http/guides/2-typegen.mdx) can automatically infer the types and generate the schema for you. This is a great way to keep your schema up to date and save time on manual type definitions.

:::

```ts title='schema.ts'
import { HttpSchema } from '@zimic/http';

interface User {
  username: string;
}

interface RequestError {
  code: string;
  message: string;
}

type Schema = HttpSchema<{
  '/users': {
    POST: {
      request: { body: User };
      response: {
        201: { body: User };
        400: { body: RequestError };
        409: { body: RequestError };
      };
    };

    GET: {
      request: {
        headers: { authorization: string };
        searchParams: {
          query?: string;
          limit?: number;
        };
      };
      response: {
        200: { body: User[] };
        400: { body: RequestError };
        401: { body: RequestError };
      };
    };
  };

  '/users/:userId': {
    PATCH: {
      request: {
        headers: { authorization: string };
        body: Partial<User>;
      };
      response: {
        204: {};
        400: { body: RequestError };
      };
    };
  };
}>;
```

### Creating an interceptor {#http-creating-an-interceptor}

With the schema defined, you can now create an [HTTP interceptor](/docs/zimic-interceptor/api/http/2-http-interceptor.mdx).

`@zimic/interceptor` provides a [`createHttpInterceptor`](/docs/zimic-interceptor/api/http/1-create-http-interceptor.mdx) function that takes the schema as a type parameter and returns an interceptor instance. It allows you to intercept HTTP requests, validate their contents, and return mock responses, all automatically typed based on the schema. The `baseURL` option represents the scope of the interceptor and points to the URL that your application will use to make requests.

```ts
import { createHttpInterceptor } from '@zimic/interceptor/http';

const interceptor = createHttpInterceptor<Schema>({
  baseURL: 'http://localhost:3000',
});
```

You can also set other options, such as the interceptor type and how unhandled requests should be treated. Refer to the [`createHttpInterceptor` API reference](/docs/zimic-interceptor/api/http/1-create-http-interceptor.mdx) for more details.

:::info INFO: <span>Choosing your interceptor type</span>

HTTP interceptors are available in two types: `local` (default) and `remote`.

<Tabs groupId="zimic-http-interceptor-type">
  <TabItem value="local" label="Local interceptor">

```ts
import { createHttpInterceptor } from '@zimic/interceptor/http';

const interceptor = createHttpInterceptor<Schema>({
  // highlight-next-line
  type: 'local',
  baseURL: 'http://localhost:3000',
});
```

  </TabItem>

  <TabItem value="remote" label="Remote interceptor">

```ts
import { createHttpInterceptor } from '@zimic/interceptor/http';

const interceptor = createHttpInterceptor<Schema>({
  // highlight-next-line
  type: 'remote',
  baseURL: 'http://localhost:3000',
});
```

  </TabItem>
</Tabs>

When an interceptor is `local`, Zimic uses [MSW](https://github.com/mswjs/msw) to intercept requests _in the same process_ as your application. This is the simplest way to start mocking requests and does not require any server setup.

Interceptors with type `remote` use a dedicated [interceptor server](/docs/zimic-interceptor/cli/1-server.md) to handle requests. This opens up more possibilities for mocking, such as handling requests from multiple applications. It is also more robust because it uses a regular HTTP server and does not depend on local interception algorithms.

Learn more about [local interceptors](/docs/zimic-interceptor/guides/http/1-local-http-interceptors.md) and [remote interceptors](/docs/zimic-interceptor/guides/http/2-remote-http-interceptors.md) to see which one fits your needs. We recommend starting with local interceptors, as they are easier to get started with, and moving to remote interceptors if your use case is best served by them.

:::

## Interceptor lifecycle {#http-interceptor-lifecycle}

### Starting an interceptor {#http-starting-an-interceptor}

To intercept requests, an interceptor must be started with [`interceptor.start()`](/docs/zimic-interceptor/api/http/2-http-interceptor.mdx#interceptorstart). This is usually done in a `beforeAll` hook in your test suite.

```ts
beforeAll(async () => {
  // highlight-next-line
  await interceptor.start();
});
```

:::info INFO: <span>Local interceptors in browsers</span>

If you are using a [local interceptor](/docs/zimic-interceptor/guides/http/1-local-http-interceptors.md) in a **browser** environment, you must first [initialize a mock service worker](/docs/zimic-interceptor/cli/2-browser.md#zimic-interceptor-browser-init) in your public directory before starting the interceptor.

:::

:::info INFO: <span>Remote interceptors and interceptor servers</span>

If you are using a [remote interceptor](/docs/zimic-interceptor/guides/http/2-remote-http-interceptors.md), the `baseURL` should point to a running [interceptor server](/docs/zimic-interceptor/cli/1-server.md), which is configured by the interceptor to handle requests. Learn more about [starting remote HTTP interceptors](/docs/zimic-interceptor/guides/http/2-remote-http-interceptors.md#starting-an-interceptor).

:::

### Clearing an interceptor {#http-clearing-an-interceptor}

When using an interceptor in tests, it's important to clear it between tests to avoid that one test affects another. This is performed with [`interceptor.clear()`](/docs/zimic-interceptor/api/http/2-http-interceptor.mdx#interceptorclear), which resets the interceptor and handlers to their initial states.

<Tabs groupId="zimic-http-interceptor-type">
  <TabItem value="local" label="Local interceptor">

```ts
beforeEach(() => {
  // highlight-next-line
  interceptor.clear();
});
```

  </TabItem>

  <TabItem value="remote" label="Remote interceptor">

```ts
beforeEach(async () => {
  // highlight-next-line
  await interceptor.clear();
});
```

  </TabItem>
</Tabs>

Learn more about how interceptors support [declarative assertions](/docs/zimic-interceptor/guides/http/7-declarative-assertions.mdx) to keep your tests clean and readable.

### Stopping an interceptor {#http-stopping-an-interceptor}

After the interceptor is no longer needed, such as at the end of your test suite, you can stop it with [`interceptor.stop()`](/docs/zimic-interceptor/api/http/2-http-interceptor.mdx#interceptorstop).

```ts

  await interceptor.stop();

```

## Mocking requests {#http-mocking-requests}

You can now use the interceptor to handle requests and return mock responses. All paths, methods, parameters, requests, and responses are typed by default based on the schema.

<Tabs groupId="zimic-http-interceptor-type">
  <TabItem value="local" label="Local interceptor">

```ts
test('example', () => {
  const users: User[] = [{ username: 'me' }];

  //  highlight-start
  interceptor
    .get('/users')
    .with({
      headers: { authorization: 'Bearer my-token' },
      searchParams: { query: 'u' },
    })
    .respond({
      status: 200,
      body: users,
    })
    .times(1);
  //  highlight-end

  // Run the application and make requests...
});
```

  </TabItem>

  <TabItem value="remote" label="Remote interceptor">

```ts
test('example', async () => {
  const users: User[] = [{ username: 'me' }];

  //  highlight-start
  await interceptor
    .get('/users')
    .with({
      headers: { authorization: 'Bearer my-token' },
      searchParams: { query: 'u' },
    })
    .respond({
      status: 200,
      body: users,
    })
    .times(1);
  //  highlight-end

  // Run the application and make requests...
});
```

  </TabItem>
</Tabs>

The remote example awaits each handler declaration because [remote interceptor operations are asynchronous](/docs/zimic-interceptor/guides/http/2-remote-http-interceptors.md#mocking-requests).

For checks that a restriction cannot express, see [inspecting intercepted requests](/docs/zimic-interceptor/guides/http/7-declarative-assertions.mdx#inspecting-intercepted-requests).

## Your first interceptor {#websocket-your-first-interceptor}

### Declaring a schema {#websocket-declaring-a-schema}

To start using a WebSocket interceptor, declare a WebSocket schema using [`@zimic/ws`](/docs/zimic-ws/guides/1-schemas.md). The schema represents the structure of your WebSocket service, including the paths and the messages exchanged by clients and servers.

```ts title='schema.ts'
import { WebSocketSchema } from '@zimic/ws';

type ChatMessage =
  | { type: 'message'; data: { text: string } }
  | { type: 'typing'; data: { username: string } }
  | { type: 'presence'; data: { online: boolean } };

type Schema = WebSocketSchema<{
  '/chat': {
    message: ChatMessage;
  };
}>;
```

### Creating an interceptor {#websocket-creating-an-interceptor}

With the schema defined, you can now create a [WebSocket interceptor](/docs/zimic-interceptor/api/ws/2-websocket-interceptor.mdx).

`@zimic/interceptor` provides a [`createWebSocketInterceptor`](/docs/zimic-interceptor/api/ws/1-create-websocket-interceptor.mdx) function that takes the schema as a type parameter and returns an interceptor instance. It allows you to intercept WebSocket connections and messages, validate their contents, and send mock server messages, all automatically typed based on the schema. The `baseURL` option represents the scope of the interceptor and points to the URL that your application will use to open WebSocket connections.

```ts
import { createWebSocketInterceptor } from '@zimic/interceptor/experimental/ws';

const interceptor = createWebSocketInterceptor<Schema>({
  baseURL: 'ws://localhost:3000',
});
```

You can also set other options, such as the interceptor type and how unhandled messages should be treated. Refer to the [`createWebSocketInterceptor` API reference](/docs/zimic-interceptor/api/ws/1-create-websocket-interceptor.mdx) for more details.

:::info INFO: <span>Choosing your interceptor type</span>

WebSocket interceptors are available in two types: `local` (default) and `remote`.

<Tabs groupId="zimic-websocket-interceptor-type">
  <TabItem value="local" label="Local interceptor">

```ts
import { createWebSocketInterceptor } from '@zimic/interceptor/experimental/ws';

const interceptor = createWebSocketInterceptor<Schema>({
  // highlight-next-line
  type: 'local',
  baseURL: 'ws://localhost:3000',
});
```

  </TabItem>

  <TabItem value="remote" label="Remote interceptor">

```ts
import { createWebSocketInterceptor } from '@zimic/interceptor/experimental/ws';

  // highlight-next-line
  type: 'remote',
  baseURL: 'ws://localhost:3000',
});
```

  </TabItem>
</Tabs>

When an interceptor is `local`, Zimic uses [MSW](https://github.com/mswjs/msw) to intercept connections opened with `globalThis.WebSocket` _in the same process_ as your application. This is the simplest way to start mocking WebSocket messages and does not require any server setup.

Interceptors with type `remote` use a dedicated [interceptor server](/docs/zimic-interceptor/cli/1-server.md) to handle connections and messages. This opens up more possibilities for mocking, such as handling connections from multiple applications or from WebSocket libraries that do not use `globalThis.WebSocket`.

Learn more about [local interceptors](/docs/zimic-interceptor/guides/ws/1-local-websocket-interceptors.md) and [remote interceptors](/docs/zimic-interceptor/guides/ws/2-remote-websocket-interceptors.md) to see which one fits your needs. We recommend starting with local interceptors, as they are easier to get started with, and moving to remote interceptors if your use case is best served by them.

## Mocking messages {#websocket-mocking-messages}

You can now use the interceptor to handle connections and messages. All paths, messages, restrictions, and responses are typed by default based on the schema.

Use [`interceptor.connection()`](/docs/zimic-interceptor/api/ws/2-websocket-interceptor.mdx#interceptorconnection) to create a [connection handler](/docs/zimic-interceptor/api/ws/4-websocket-connection-handler.mdx), which accepts or rejects connection attempts, and [`interceptor.message()`](/docs/zimic-interceptor/api/ws/2-websocket-interceptor.mdx#interceptormessage) to create a [message handler](/docs/zimic-interceptor/api/ws/3-websocket-message-handler.mdx), which responds to client messages.

<Tabs groupId="zimic-websocket-interceptor-type">
  <TabItem value="local" label="Local interceptor">

```ts
test('example', () => {
  //  highlight-start
  interceptor.connection('/chat').respond({ action: 'accept' }).times(1);

  interceptor
    .message('/chat')
    .with({ type: 'message' })
    .respond((message) => ({
      type: 'presence',
      data: { online: message.data.text.length > 0 },
    }))
    .times(1);
  //  highlight-end

  // Run the application, open connections, and send messages...
});
```

  </TabItem>

  <TabItem value="remote" label="Remote interceptor">

```ts
test('example', async () => {
  //  highlight-start
  await interceptor.connection('/chat').respond({ action: 'accept' }).times(1);

  await interceptor
    .message('/chat')

    .respond((message) => ({
      type: 'presence',
      data: { online: message.data.text.length > 0 },
    }))
    .times(1);
  //  highlight-end

  // Run the application, open connections, and send messages...
});
```

  </TabItem>
</Tabs>

The remote example awaits each handler declaration because [remote interceptor operations are asynchronous](/docs/zimic-interceptor/guides/ws/2-remote-websocket-interceptors.md#mocking-messages).

For checks that a restriction cannot express, see [inspecting messages and connections](/docs/zimic-interceptor/guides/ws/5-declarative-assertions.mdx#inspecting-messages-and-connections).
